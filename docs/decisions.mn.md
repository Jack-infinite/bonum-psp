# Дизайны шийдвэрүүд

[English](./decisions.md) | **Монгол**

Bonum-ын баримт бичиг нээлттэй үлдээсэн, эсвэл хуудсууд нь хоорондоо зөрчилдсөн газруудад хийсэн
сонголтуудын товч тэмдэглэл. Бичлэг бүр бид юу хийдэг, яагаад гэдгийг хэлнэ. Албан ёсны баримт бичиг
<https://psp.bonum.mn/v2/integration-guide.html> хаягт байна.

## D1. Redirect-ийг хэзээ ч дагахгүй

Хүсэлтүүд `fetch(..., { redirect: 'manual' })` ашигладаг бөгөөд аливаа 3xx (эсвэл opaque redirect)
`BonumUnexpectedResponseError` болно. Зорилго нь redirect хэзээ ч `x-merchant-key` header-ийг өөр
хост руу аваачихгүй байх. Бид `redirect: 'error'` ашиглахыг хүссэн боловч Cloudflare Workers энэ
утгыг хүлээн авдаггүй (зөвхөн `follow`, `manual` утгыг хүлээн авдаг). Тиймээс бүх орчинд ижил
баталгааг өгөх арга нь `manual`.

## D2. `getByOrderId` яг нэг төлбөр буцаана

V2 API лавлах нь order id-аар хайх хүсэлт нэг төлбөрийн объект буцаана гэж баримтжуулсан. Bonum-ын
хуучин wallet-ийн заавар нэг order id дор хэд хэдэн оролдлоготой массив харуулдаг. Массив ирэхэд
SDK аль оролдлогыг тооцохыг таахын оронд `BonumUnexpectedResponseError` шиднэ. Баримт бичиг нь
мерчантуудад төлбөрийн оролдлого бүрт шинэ `order_id` ашиглаж, `paymentId`-г хадгалахыг заадаг.

## D3. Мөнгө хамаарах газар хатуу, бусад газар уян хатан

- Үл мэдэгдэх төлбөрийн `status` бол алдаа: бараа илгээх эсэхийг шийддэг код ойлгохгүй утгатай
  хэзээ ч тулгарах ёсгүй.
- Webhook-ийн `status` нь түүний `eventType`-тэй тэнцүү байх ёстой (Phase 3).
- Дутуу `providerReference` эсвэл `failureReason` нь `null` болно, учир нь Bonum-ын зарим жишээнд
  тэдгээр байдаггүй.
- `walletType` (болон webhook-ийн `binCategory`) нь нээлттэй string union. Тиймээс Bonum дараа нь
  шинэ wallet нэмэхэд build ч, webhook handler ч эвдрэхгүй.
- `statusUrl` болон `awaitUrl` энгийн string хэвээр хадгалагдана. SDK тэднийг хэзээ ч дууддаггүй;
  URL бүрийг өөрийн base URL болон баталгаажуулсан `paymentId`-аас бүрдүүлдэг.

## D4. MCP сервер production орчинд тестийн webhook-д гарын үсэг зурахгүй

`BONUM_ENV=production` үед `create_test_webhook` болон `send_test_webhook` гарын үсэг зурахаас
татгалзана. Зөв гарын үсэгтэй хуурамч `AUTHORIZED` үйл явдлыг бодит endpoint руу таван минутын
турш дахин илгээж болох юм. Энэ бол хурд сааруулагч болохоос аюулгүй байдлын хил биш (`BONUM_ENV`
зөвхөн API хостыг сонгодог). Тиймээс баримт бичиг MCP серверт зөвхөн sandbox-ийн нууц түлхүүрийг
өгөхийг бас заадаг. `send_test_webhook` мөн redirect дагадаггүй тул гарын үсэгтэй body хэзээ ч
хэрэглэгчийн нэрлээгүй хост руу дахин илгээгдэхгүй.

## D5. `verify_webhook`-ийн `ignoreTimestamp` цагийг тогтоодог

Барьж авсан webhook-ийг дахин тоглуулахад таван минутын цонхыг алгасах хэрэгтэй. MCP хэрэгсэл
үүнийг "одоо" гэсэн цагийг header-ийн өөрийн timestamp-д тохируулах замаар хийдэг. Тиймээс SDK-д
мерчант андуурч асааж болох "цагийн шалгалтыг алгасах" тохиргоо байхгүй.

## D6. Токены хэлбэр

Google Pay-ийн токен string байх ёстой (`tokenizationData.token`, өөрчлөгдөөгүй); объект бол
validation алдаа. Apple Pay-ийн токен нь `PKPaymentToken` объект эсвэл түүний JSON string байж болно,
учир нь mobile bridge-үүд ихэвчлэн string дамжуулдаг. Зөвхөн дээд түвшнийг шалгадаг; токен
хөндөгдөлгүй илгээгдэнэ. Bonum хязгаарыг зөвхөн Apple Pay-д заасан ч `order_id` хоёр wallet-ийн хувьд
128 тэмдэгтээр хязгаарлагдана: хатуу дүрэм нь банк дээр бүтэлгүйтэхийн оронд эрт бүтэлгүйтдэг.

## D7. Retry-уудыг хамарсан хугацааны хязгаар

Анхдагч утгууд (оролдлого бүрт 15 с, 2 retry) нь wallet цонх нээлттэй байдаг ойролцоогоор 30
секундээс удаан үргэлжилж болно. Шинэ тохиргоо нэмэхийн оронд дуудагчийн `AbortSignal` нь
retry-уудын хоорондох хүлээлтийг ч цуцалдаг. Wallet-ийн жишээнүүд submit болон `waitForResult`-д
нэг нийт хугацааны хязгаар ашигладаг.

## D8. Хувилбарын string автоматаар үүсдэг

`scripts/sync-version.mjs` нь `pnpm build` болон Changesets-ийн version алхмын үеэр `package.json`
бүрээс `src/version.ts` файлыг бичдэг. Энэ файл commit хийгдсэн бөгөөд зөрвөл тест бүтэлгүйтнэ.
Runtime код хэзээ ч `package.json` уншдаггүй тул SDK файлын систем байхгүй орчинд ч ажиллана.

## D9. Sandbox бодит мөнгө хөдөлгөж магадгүй

Bonum-ын wallet-ийн жишээн дэх тайлбарт туршилтын орчин банкны гүйлгээг бодитоор хийдэг гэж бичсэн
байдаг. Баримт бичиг үүнийг сануулдаг бөгөөд энэ репогийн тест болон MCP хэрэгслүүдийн аль нь ч
төлбөр илгээдэггүй.

## D10. Илгээлт аль хэдийн шийдэгдсэн төлөвтэй буцаж ирж болно

Bonum `order_id`-г idempotency түлхүүр гэж үзэж, дахин ашиглахад одоо байгаа төлбөрийг буцаадаг.
Тэр дахин хариу ямар төлөвтэй ирэхийг баримт бичиг хэлдэггүй. Тиймээс `PaymentSubmission.status`
нь зөвхөн `PENDING` биш, аливаа `PaymentStatus` байж болохоор тодорхойлогдсон. Эс бөгөөс хариу
алдагдсаны дараах автомат retry амжилттай төлбөрийг алдаа болгож, хэрэглэгч хоёр дахин төлж магадгүй.

## D11. Тоон дүн болон валютыг хүлээн авна

Лавлах нь lookup-ийн `amount` болон `currency`-г string гэж баримтжуулдаг боловч Bonum-ын зарим
жишээ тоо харуулдаг (`150.5`, `496`). SDK тэднийг `string` төрөлтэй хэвээр нь үлдээж, JSON тоог
утгыг нь хадгалдаг `String()`-ээр хөрвүүлдэг. Тиймээс Bonum талын форматын өөрчлөлт тулгалтыг
(reconciliation) зогсоож чадахгүй. Утгуудыг өөр ямар ч байдлаар дахин бичдэггүй; `normalizeCurrency()`
нь хүсвэл ашиглах нэмэлт функц.

## D12. Retry болон алдааны классууд

Сүлжээний алдаа, timeout, 429, 500, 502, 503, 504-ийг full-jitter exponential backoff-оор (500 мс
суурь, 8 с дээд хязгаар) дахин оролддог. Бусад статус, түүний дотор 501, дахин оролдогдохгүй.
`Retry-After`-ийг 60 с хүртэл хүндэтгэнэ; `BonumRateLimitError.retryAfterMs` нь Bonum-ын илгээсэн
хязгаарлаагүй утгыг мэдээлдэг. Тусгай класс байхгүй статусууд (403, 409, 422, …) суурь
`BonumAPIError` шиднэ. `maxRetries` нь 0–10-аар хязгаарлагдсан тул үсгийн алдаа хүсэлтийг хэдэн
минутаар завгүй байлгахгүй.

## D13. Мерчант түлхүүрийн цэвэрлэгээ

Мерчант түлхүүрийн эхэн, төгсгөлийн хоосон зайг арилгадаг, учир нь environment файл болон нууц
хадгалах сангууд ихэвчлэн шинэ мөрийн тэмдэгт нэмдэг. Дотроо хоосон зай эсвэл удирдлагын тэмдэгттэй
түлхүүрийг татгалзах бөгөөд алдааны мессежид түлхүүр хэзээ ч ордоггүй.

## D14. Тестийн hook-ууд энгийн тохиргоо

`sleep` болон `random` нь тестийн hook гэж баримтжуулсан client-ийн тохиргоо. Ингэснээр retry-ийн
тестүүд хуурамч timer-гүйгээр детерминист ажиллаж, мерчантууд өөрсдийн тестэд ижил hook-уудыг
ашиглаж болно.

## D15. Үл мэдэгдэх webhook үйл явдлын төрлийг хүлээн авна

SDK-ийн мэдэхгүй `eventType`-тэй, зөв гарын үсэгтэй webhook нь
`BonumWebhookError('unsupported_event_type')` шиднэ. Handler туслахууд түүнд
`200 { "received": true, "ignored": true }` гэж хариулна. 4xx хариулбал мерчантын хэзээ ч
боловсруулж чадахгүй үйл явдлыг Bonum бууж өгөх хүртлээ дахин дахин илгээнэ. Үйл явдлын төрлийг
бусад талбараас өмнө шалгадаг, учир нь шинэ төрөл өөр бүтэцтэй байж магадгүй. `onError` түүнийг
хүлээн авсаар байгаа тул log-д харагдана.

## D16. Handler-ийн алдаа нуугдахгүй

`onEvent` алдаа шидэхэд (эсвэл баталгаажуулалт гэнэтийн байдлаар бүтэлгүйтэхэд) handler-ууд
`onError`-ийг дуудаж, 500 гэж хариулдаг тул Bonum дахин илгээнэ. `onError` өгөөгүй бол Fetch
handler алдааг дахин шиддэг, Express adapter `next(error)`-ийг дууддаг. Дараа нь framework алдааг
log-д бичиж, 500 гэж хариулна. Алдааг чимээгүй залгивал Bonum дахин оролдохоо болих хүртэл эвдэрсэн
handler нуугдмал үлдэх байсан. Татгалзсан webhook (буруу гарын үсэг, хуучирсан timestamp) үргэлж
зөвхөн шалтгааныг нэрлэсэн 400 хариу авна.

## D17. Bonum өөрчилж болох талбаруудыг сул төрөлжүүлнэ

`PaymentAuthorizedEvent` болон `PaymentFailedEvent` нь зөвхөн `eventType`, `status`-аараа ялгаатай.
`providerReference` болон `failureReason` хоёуланд нь `string | null`: татгалзсан төлбөр банкны
лавлагаатай байж болох бөгөөд үүнээс болж жинхэнэ webhook-ийг татгалзвал үйл явдал алдагдана.
`status` нь `eventType`-тэй тэнцүү байх ёстой хэвээр (D3).

## D18. Webhook-ийн нууц түлхүүрийн боловсруулалт

Нууц түлхүүрүүдийг мерчант түлхүүр шиг (D13) хоосон зайгаас цэвэрлэдэг бөгөөд нууц түлхүүрүүдийн
массив нь солилтыг (rotation) дэмждэг. Түлхүүрүүдийг Web Crypto-оор нэг удаа import хийж, cache-д
хадгалдаг; бүтэлгүйтсэн import-ийг дараагийн дуудлагад дахин оролддог. `toleranceSeconds` нь
анхдагчаар Bonum-ын 300 бөгөөд 1–3600-аар хязгаарлагдсан тул replay хамгаалалтыг санамсаргүйгээр
унтрааж болохгүй. Timestamp шалгалтыг алгасах тохиргоо байхгүй (D5-ийг үзнэ үү).

## D19. Жишээнүүд одоогийн хэрэгслүүд дээр шууд ажиллана

Express жишээ TypeScript-ээ Node-ийн type stripping-ээр шууд ажиллуулдаг (Node 22.18 эсвэл түүнээс
хойш), тиймээс build алхам хэрэггүй. Next.js жишээ TypeScript 7 дээр `next build`-ээр бүтдэг тул
хаана ч TypeScript 6 руу буцах шаардлагагүй. Түүний route handler эхний хүсэлт дээр webhook
шалгагчийг үүсгэдэг тул `next build` нууц түлхүүр шаардахгүй.

## D20. MCP сервер бас жижиг сан (library)

CLI-аас гадна `bonum-psp-mcp` нь `createBonumMcpServer(deps)` болон `depsFromEnv(env)`-ийг export
хийдэг. Тиймээс серверийг өөр програм дотор (жишээ нь MCP SDK-ийн handler-уудаар HTTP дээр)
ажиллуулж, process дотор тестлэж болно. `deps` нь CLI-ийн орчноос уншдаг бүх зүйлийг агуулж чадна:
base URL, анхааруулгууд, remote target-ийн унтраалга, redactor, мөн brief-д заасан client, `fetch`,
`now`. `webhooks` нь `BonumWebhooks` биш, хоёр методтой `WebhookToolkit` (verify ба sign), учир нь
тестийн хэрэгслүүд ижил нууц түлхүүрээр гарын үсэг зурдаг. Нууц түлхүүр closure дотор үлддэг. Smoke
тест одоогийн болон хуучин MCP handshake хоёуланг нь шалгадаг, учир нь client-ууд өөр өөр цагт
шинэчлэгддэг.

## D21. MCP сервер үргэлж эхэлнэ

`depsFromEnv` хэзээ ч алдаа шиддэггүй. Дутуу эсвэл буруу утга нь зөвхөн түүнийг шаарддаг
хэрэгслүүдийг унтраадаг. Ийм утга анхааруулга болж, CLI эхлэхдээ түүнийг stderr-д хэвлэдэг,
`check_connection` жагсаадаг, холбогдох хэрэгслүүд давтан хэлдэг. `BONUM_ENV` яг `sandbox` эсвэл
`production` байх ёстой. Бусад утга анхааруулгатайгаар sandbox руу буцна: хэзээ ч таамагладаггүй
SDK-аас ялгаатай нь MCP сервер бол хөгжүүлэлтийн хэрэгсэл бөгөөд sandbox бол аюулгүй тал.
`BONUM_MCP_ALLOW_REMOTE_WEBHOOK_TARGETS` зөвхөн `true`, `false`-ийг хүлээн авна; бусад утга
анхааруулга өгч `false` хэвээр үлдэнэ.

## D22. MCP серверт API timeout богино

MCP серверийн client нь SDK-ийн 15 с, 2 retry-ийн оронд 10 с timeout, нэг retry ашигладаг.
Ингэснээр хэрэгслийн дуудлага ойролцоогоор 20 секундэд хариулж, түгээмэл MCP client-уудын хэрэгслийн
дуудлагын хязгаарт багтана. `wait_for_payment_result` нь SDK-ийн өөрийн дүрмийг хадгалдаг: retry
байхгүй, HTTP timeout нь `waitMs + 5 s`.

## D23. Хэрэгслийн handler-ууд өөрсдийн алдааг барьдаг

MCP SDK нь exception-ийг түүхий мессежийг агуулсан алдааны үр дүн болгодог бөгөөд энэ нь нууц
мэдээллийг далдлах алхмыг (redaction) алгасна. Тиймээс хэрэгсэл бүр алдааг өөрөө барьж, `isError`
үр дүн болгон буцаадаг. Дараа нь бүх текст болон `structuredContent` нь redactor-оор дамждаг. Тэр нь
тохируулсан түлхүүр болон нууц түлхүүрийг (урт нь эхэлж) `[redacted]`-аар солидог. SDK-ийн мессеж
анхнаасаа нууц мэдээлэл агуулдаггүй тул энэ бол хамгаалалтын сүүлчийн шугам. Тест бүрийн дараа MCP
тестийн багц серверийн илгээсэн бүх зүйлд тохируулсан түлхүүр болон нууц түлхүүр байгаа эсэхийг
шалгадаг. Тестийн нууц түлхүүрүүд баримт бичгийн placeholder-уудаас ялгаатай, учир нь prompt-ууд
тэдгээр placeholder-ийг хууль ёсоор харуулж болно.

## D24. Production орчны үр дүн, алдаа ч бас, тэмдэглэгээтэй

`BONUM_ENV=production` үед Bonum-ыг дууддаг хэрэгслийн үр дүн бүрийн текст production анхааруулгаар
эхэлнэ. Алдааны үр дүн ч мөн адил, учир нь production орчны 404 ч бодит өгөгдөл. Амжилттай үр
дүнгүүд `structuredContent`-д `environment` талбарыг бас агуулдаг. `create_test_webhook` болон
`send_test_webhook` огт ажиллахаас татгалзана (D4).

## D25. `send_test_webhook` endpoint-ийг хэрхэн дүгнэдэг

`scenario` анхдагчаар `all`, `create_test_webhook`-ийн `eventType` анхдагчаар `AUTHORIZED` тул
"миний webhook-ийг тестлээрэй" гэхэд зөвхөн URL хангалттай. Сценариуд ар араасаа ажилладаг тул
давхардсан хос бусад илгээлттэй холилдохгүй. Хуурамч webhook нь шинэ санамсаргүй нууц түлхүүрээр
гарын үсэг зурагдсан, хуучирсан webhook нь зөв гарын үсэгтэй боловч 10 минутын настай (tolerance-ийн
хоёр дахин). Аль нэгэнд нь 2xx хариулбал аюулгүй байдлын бүтэлгүйтэл бөгөөд хураангуй түүгээр
эхэлнэ. Аль нэгэнд нь 5xx хариулбал анхааруулга, учир нь Bonum дахин оролдоно. 3xx үргэлж
бүтэлгүйтэл: хэрэгсэл redirect дагадаггүй (D4) тул handler үйл явдлыг хэзээ ч хараагүй.

## D26. Нэмэлт гаралтын талбарууд

Зарим MCP хэрэгсэл brief-д жагсаасанаас илүү талбар буцаадаг. `verify_webhook` нь `reason`-ийн
SDK-ийн тайлбар болох `message`-ийг нэмдэг. `create_test_webhook` нь гарын үсэг таван минутын
цонхноос гарах цагийг заах `expiresAt`-ийг нэмдэг. Төлбөрийн хэрэгслүүд өөрчлөгдөөгүй `currency`-ийн
хажууд `normalizedCurrency`-ийг нэмдэг (D11). `check_connection` нь `auth`-ийг `ok`, `invalid_key`,
`unreachable`, `error` эсвэл `not_configured` гэж мэдээлж, тохиргооны анхааруулгуудыг нэмдэг.

## D27. Prompt-ууд бие даасан

Зарим MCP client хэрэгсэл болон prompt-ийг дэмждэг ч resource-ийг дэмждэггүй. Тиймээс prompt бүр
түшиглэдэг дүрмүүдээ өөрийн текстдээ бичдэг бөгөөд `bonum://` resource-ууд руу зөвхөн нэмэлт
уншлагад заадаг.

## D28. Бүх хэрэгсэлд TypeScript 7

TypeScript 7-д хуучин compiler API байхгүй, гэхдээ хэрэгслүүдийн аль нь ч түүнийг шаарддаггүй.
tsdown нь declaration-уудыг `isolatedDeclarations` (oxc) замаар үүсгэдэг, knip oxc-оор parse хийдэг,
attw өөртөө агуулдаг TypeScript 5.6-аар шинжилдэг. `expectTypeOf` төрлийн тестүүдийг Vitest-ийн
typecheck горимын оронд тестийн файлууд дээрх ердийн `tsc` ажиллагаа (`pnpm typecheck`) шалгадаг.
Ямар ч хэрэгсэлд TypeScript 6 руу буцах шаардлага гараагүй (D19-ийг бас үзнэ үү).

## D29. MCP серверийг хэрхэн тестлэдэг

Хэрэгслүүдийг process дотор жинхэнэ MCP `Client`-ээр тестлэдэг. Тэр нь серверт MCP SDK-ийн HTTP
handler-аар (`createMcpHandler`) process доторх `fetch` ашиглан хандах бөгөөд энэ нь протоколын
одоогийн хувилбарыг хамардаг. SDK-ийн in-memory transport зөвхөн 2025 оны хувилбаруудыг хамардаг.
Stdio замыг бүтээсэн `dist/cli.js`-ийг эхлүүлдэг smoke тест хамардаг (D20).

## D30. Задлагдаагүй `${VAR}` лавлагааг үл тооно

Санал болгосон `.mcp.json` нь нууц мэдээллийг `${BONUM_MERCHANT_KEY}` хэлбэрээр дамжуулдаг.
Хувьсагч тохируулагдаагүй үед Claude Code үгчилсэн текстийг сервер рүү өгдөг. Тэгвэл сервер `${…}`
текстийг нууц түлхүүр болгон гарын үсэг зурах, эсвэл түлхүүр болгон Bonum-ыг дуудах байсан.
`depsFromEnv` нь `${…}` агуулсан аливаа утгыг тохируулагдаагүй гэж үзэж, export хийх ёстой
хувьсагчийг нэрлэсэн анхааруулга нэмж, зөвхөн холбогдох хэрэгслүүдийг унтраадаг (D21).

## D31. `branch_id` болон Apple Pay-ийн `amount` бол сонголттой дамжуулалт

Одоогийн API лавлах `branch_id`-г зөвхөн интеграцын зааварт биш, хоёр wallet-ийн хувьд жагсаадаг.
SDK түүнийг `amount`-ийн адил зөвхөн дуудагч өгсөн үед илгээдэг. Bonum-ын хуудсууд Apple Pay-ийн
`amount`-ийг зөвхөн жишээнд харуулдаг бөгөөд токен доторх дүнг дарж бичих эсэхийг хэзээ ч хэлдэггүй.
SDK мерчантын дамжуулсан зүйлийг яг тэр чигээр нь илгээдэг бөгөөд баримт бичиг мерчантуудад дүнг
сервер дээрээ шийдэхийг заадаг.

## D32. Release-ийн дамжлага

Release нь Changesets 3-ыг `changesets/action` v2-той хамт ашигладаг. Changesets trusted publishing-д
зөвлөдгийн дагуу action-ийг дэд action-уудад хуваасан. `select-mode` нь хувилбарлах эсвэл publish
хийхийн хооронд шийддэг. `version` нь "Version Packages" pull request-ийг нээдэг (мөн
`src/version.ts`-ийг дахин үүсгэдэг, D8). `pack` нь `pnpm check` ажиллуулж, багц бүрийг
`workspace:^`-ийг дахин бичдэг `pnpm pack` командаар савладаг. `publish` нь савласан tarball-уудыг
`pnpm publish` командаар publish хийдэг. Зөвхөн `publish`-д `id-token: write` эрх бий. Changesets 3
pnpm-ийг илрүүлж, `pnpm pack`/`pnpm publish`-ийг өөрөө дууддаг. pnpm 12 бол OIDC солилцоог хийж,
npm CLI-гүйгээр provenance хавсаргадаг native executable тул runner дээрх npm хувилбар хамаагүй.
Release job-ууд dependency cache ашигладаггүй бөгөөд `--ignore-scripts` тохиргоотой суулгадаг.
Энэ нь эвдэгдсэн dependency OIDC токены хажууд юу хийж чадахыг хязгаарладаг. Action бүрийг бүтэн
commit SHA-д бэхэлсэн.

## D33. Biome-ийн хөндөхгүй файлууд

Biome 2.6 нь Markdown болон YAML-ийг бас форматлана. Дөрвөн төрлийн файлыг хассан:

- Changesets-ийн бичдэг, хувь нэмэр оруулагчдын засдаг `CHANGELOG.md` файлууд болон
  `.changeset/*.md`, учир нь форматын зөрүү Version Packages pull request дээр CI-г унагах ёсгүй;
- YAML front matter-ийг нь Biome өөрчлөх байсан `skills/**/SKILL.md`;
- үгчлэн хадгалсан Contributor Covenant болох `CODE_OF_CONDUCT.md`.

Бусад бүх зүйл, README доторх код блокууд ч бас, форматлагдаж шалгагддаг.
